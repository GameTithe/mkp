# 작업 계획

## 업무 목표와 성공 기준

- 사용자: 성능 QA 담당자 윤서(가상).
- 병목: baseline/candidate 로그를 눈으로 비교하고 있음.
- 결과: 손상·중복·워밍업 행을 구분하고 시나리오별 p95 회귀 우선순위를 JSON으로 출력.
- 증거: `CONTRACT.md` 명령의 종료코드/JSON 구조, 자체 테스트, 샘플 실행 결과.

## 조건의 상태

- 확정: CLI 옵션, 성공/실패 JSON 모양, 상태/병목 enum, 오류 종료코드 2, UTF-8(BOM 허용), 수치 오차와 중간 반올림 금지 (`CONTRACT.md`).
- 확정: 담당자 대화와 확인받은 추가 요구사항은 현재 없음(사용자 제공 `[]`).
- 가정: frame 0~2를 워밍업으로 제외, 중복 키는 `(build, scenario, frame)`이고 첫 행 유지, p95는 선형 보간, 빌드별 최소 5행, p95가 2ms 이상이면서 10% 이상 증가하면 회귀.
- 가정: 유효 build는 baseline/candidate, frame은 0 이상의 정수, scenario는 빈 문자열이 아닌 문자열, cpu/gpu는 0 이상의 유한 실수.
- 가정: frame time은 `max(cpu_ms, gpu_ms)`, candidate의 cpu/gpu p95 중 큰 쪽을 병목으로 판정(같으면 balanced), 우선순위는 regressed → stable → insufficient 및 변화율 내림차순.
- 미확인 질문:
  1. 워밍업은 frame 번호 0~2인가, 각 그룹의 처음 N개인가, 별도 마커인가?
  2. 허용 build/scenario/frame/시간 값과 잘못된 행의 정확한 처리 기준은?
  3. 중복 키, 첫/마지막 행 선택, 유효성·중복·워밍업 처리 순서는?
  4. p95는 선형 보간인가 nearest-rank인가?
  5. 최소 표본 수와 회귀 절대/상대 임계값, 경계값 포함 여부는?
  6. 병목의 balanced 허용차와 insufficient일 때의 병목 값은?
  7. items 정렬 기준과 `--scenario`/`--status` 사용 시 meta·warnings의 범위는?

## 범위 선택

- 반드시 구현: 계약 CLI, 안전한 파싱/행 검증, 집계/필터/정렬, 오류 JSON, 자체 테스트, RUNBOOK/HANDOFF/ENV 갱신.
- 제외: DB, 네트워크, UI, 외부 패키지, 설정 파일. 계약과 확인 근거가 없음.
- 안전 조치: traceback·입력 원문·개인 경로·추가 필드를 출력하지 않음.

## 구현과 위임

- 메인 에이전트가 입력 확인부터 구현·테스트·문서화까지 직접 담당. 별도 에이전트 없음.
- 입력: 계약 형식 JSON. 출력: JSON 객체 하나. 완료 조건: 자체 테스트와 공개 명령을 실제 실행해 결과 확인.

## 검증 루프

- 정상 샘플/빈 입력/필터/잘못된 JSON·행/중복/BOM/경계값을 실행하고 JSON, 종료코드, stderr를 확인.

## 판단 변경

- 담당자 답변을 받으면 위 가정을 확정값으로 바꾸고 경계 테스트를 먼저 수정한 뒤 구현을 재검증해야 함.
